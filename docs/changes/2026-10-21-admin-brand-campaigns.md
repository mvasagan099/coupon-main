# Admin-managed brand campaigns

The live CouponVault project `mrextbryyayaojorstml` now contains 15 records in `public.brand_campaigns`, created through the `admin_brand_campaigns` migration. Reapplying the seed preserves existing campaign edits. The standalone `supabase/BRAND_CAMPAIGNS_SETUP.sql` and the main all-in-one installer include the same schema and seeds; no manual SQL run is needed on this project after this deployment.

Admin → Campaigns (`/admin/campaigns`) allows editing name, category, description, colour, display order, country, published/hidden status, and linked coupon issuer. Writes check the previously loaded `updated_at` timestamp so a stale editor cannot silently replace another admin’s changes. Campaigns are hidden instead of deleted. Names, values and display styles are constrained in the database; customer input cannot change publication or issuer bindings.

The customer marketplace reads published campaign rows from Supabase, with no hardcoded fallback. Country visibility and active-account checks apply in RLS as well as the UI. Campaign coupon listings use the linked merchant’s immutable company ID, rather than matching the brand’s display name. An unlinked campaign has no purchasable inventory. Historical illustrative definitions remain only for compatibility with the separated preview-detail implementation/tests; active brand routes now use the database-backed listing and do not expose those previews.

Permissions: signed-out clients have no table access; active customers can read eligible published campaigns; only active admins can insert or update. Authenticated clients cannot delete campaigns. A security-invoker trigger updates timestamps. Live readback confirmed 15 campaigns, RLS enabled, the expected policies, no anonymous SELECT grant and no authenticated DELETE grant. No coupons, wallet balances, purchases or payment-provider settings were changed.

Validation: frontend build/lint; 19 workflow tests; an isolated PGlite/Postgres regression covers seeds, repeat migration preserving edits, anonymous denial, customer read-only access, admin editing, hidden/country visibility, locked accounts and updated timestamps. Run it with `PGLITE_MODULE=/path/to/@electric-sql/pglite node tests/campaigns-db.test.cjs` (an ordinary installation can use the package name without that variable). Browser checks use isolated fixtures to edit and hide a campaign, save it successfully, and inspect desktop/mobile and light/dark views. Admin navigation now stays within the viewport with horizontal scrolling inside its menu.

The Supabase security advisor reports no new campaign-table warning. Existing unrelated notices remain, including [executable security-definer functions](https://supabase.com/docs/guides/database/database-linter?lint=0029_authenticated_security_definer_function_executable), [anonymous access to get_companies](https://supabase.com/docs/guides/database/database-linter?lint=0028_anon_security_definer_function_executable), and [disabled leaked-password protection](https://supabase.com/docs/guides/auth/password-security#password-strength-and-leaked-password-protection). These notices were not changed as part of campaign management.
